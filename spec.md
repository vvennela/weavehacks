# Sera Technical Specification

Status: MVP specification

## 1. Purpose

Sera is a Python library that automatically improves model inference on the hardware available to the user.

The user supplies one or more Hugging Face model identifiers and representative prompts. Sera loads the models through vLLM, measures a baseline, chooses controlled experiments, rejects unsafe or low-quality configurations, and returns SeraModel runners plus a report.

Sera has two goals:

1. Make fast inference available without requiring inference-engineering knowledge.
2. Reach a strong valid configuration with fewer GPU trials than mechanistic grid search.

## 2. Product contract

The minimum call is:

    import sera

    result = sera.optimize(
        models=["Qwen/Qwen3-0.6B", "zai-org/glm-4-9b-chat-hf"],
        prompts=prompts,
    )

    result.print_summary()
    model_a, model_b = result.models

The user does not need to choose quantization, batching, parallelism, or GPU placement settings.

Sera owns model loading. It returns SeraModel wrappers with a stable generate interface. It does not return raw vLLM engine objects.

## 3. MVP scope

The MVP supports:

- One or two text-generation models
- Public or authenticated Hugging Face model repositories
- Pinned model revisions
- vLLM as the only inference runtime
- One NVIDIA GPU in Molab
- Multiple NVIDIA GPUs when the same code runs on CoreWeave
- Quick and verified validation modes
- Sequential candidate trials on one GPU
- Concurrent trials only when isolated GPUs are available
- Local SQLite persistence
- W&B Weave traces and evaluation records
- W&B Inference as the default agent-model provider

The MVP does not support:

- Training or fine-tuning
- Image, audio, or video models
- CPU or Apple Silicon inference
- Live production mutation
- Kubernetes provisioning
- Automatic model architecture conversion
- Arbitrary vLLM command-line settings generated by an agent
- More than two models in a joint placement trial

The internal data model must not assume that two is the final product limit.

## 4. Target environments

### 4.1 Hackathon environment

The primary test environment is a Molab notebook running on CoreWeave.

The verified environment provides:

- One NVIDIA RTX Pro 6000 Blackwell GPU
- 96 GB GPU memory
- Four CPUs
- 32 GB host memory
- A maximum session length of 12 hours
- Linux and Python package installation through uv

One-GPU limits are part of the design:

- Phase-one trials run sequentially.
- Tensor parallelism is inactive and must not consume a trial.
- Phase two tests two vLLM services on the same GPU.
- Sera claims better GPU use, not that it freed a second GPU.

### 4.2 CoreWeave path

CoreWeave supports vLLM on GPU nodes through its Kubernetes service and dedicated inference products. Sera does not manage a CoreWeave cluster in the MVP. The runtime adapter and configuration records must remain portable to a later CoreWeave deployment adapter.

## 5. Models used for the demonstration

The initial demonstration uses:

- Qwen/Qwen3-0.6B
- zai-org/glm-4-9b-chat-hf

Reasons:

- Both are open-weight text-generation models.
- They use different model architectures.
- vLLM lists both architectures as supported.
- Their different sizes exercise different optimization decisions.
- Both can fit within the Molab GPU budget.

The Qwen model uses the Apache 2.0 license. The GLM model uses its own license. Product text must call the pair open-weight, not universally open-source.

Every run records the exact Hugging Face revision SHA. A run must not compare floating repository revisions.

## 6. Public API

### 6.1 Quick mode

    result = sera.optimize(
        models=["Qwen/Qwen3-0.6B"],
        prompts=["Explain paged attention in simple English."],
    )

Quick mode requires:

- At least one model identifier
- At least one representative prompt
- A W&B API key in the WANDB_API_KEY environment variable

Quick mode supplies:

- A standard concurrency sweep
- A default output limit
- A default experiment budget
- A behavior-preservation quality proxy
- A latency-first selection policy

Quick mode must state that task quality was not verified.

### 6.2 Verified mode

    result = sera.optimize(
        models=[model_a, model_b],
        prompts=prompts,
        evaluation=evaluate_answer,
        constraints=[
            sera.Constraints(p95_latency_ms=250, quality_floor=0.99),
            sera.Constraints(p95_latency_ms=400, quality_floor=0.99),
        ],
        workload=sera.Workload(concurrency=[1, 2, 4, 8]),
        budget=sera.Budget(max_candidate_trials=8),
    )

Verified mode requires:

- A deterministic or versioned evaluation callable
- A quality floor
- A latency requirement for each model
- A workload definition

### 6.3 Result types

SeraResult contains:

- models: ordered list of SeraModel
- recommended: selected configuration or no-safe-improvement
- frontier: valid non-dominated configurations
- baselines: baseline results
- trials: every proposed and executed trial
- rejected: candidates rejected without execution
- report: structured summary data
- weave_url: trace URL when Weave is enabled

SeraModel contains:

- model_id
- revision
- configuration
- generate
- close
- metrics_snapshot

SeraModel.generate accepts text or chat messages and returns a normalized Sera response. The wrapper hides whether vLLM runs in-process or as a managed local server.

## 7. Defaults

The defaults exist to keep the minimum call small.

- Default output limit: 64 new tokens
- Default concurrency sweep: 1, 2, 4, and 8
- Default warm-up requests: one full pass through the prompt sample, capped at 16 requests
- Default measured requests: three passes through the prompt sample, capped at 96 requests
- Default candidate budget: eight trials across both phases
- Reserved phase-two budget for two models: two trials
- Default quality tolerance: candidate proxy score must be at least 0.99 relative to the baseline
- Default objective: pass quality first, then minimize p95 end-to-end latency, then minimize peak GPU memory
- Default stop rule: stop after two rounds without frontier improvement or when the budget ends

Defaults must be printed in the summary and stored in the ledger.

## 8. System architecture

### 8.1 AI roles

Sera uses five AI roles:

1. Quantization specialist
2. Batching specialist
3. Parallelism specialist
4. Arbiter
5. Frontier reader

The agents use W&B Inference through its OpenAI-compatible API. The user supplies the W&B API key through the environment. The agent model is configurable. The MVP default is openai/gpt-oss-20b.

Each agent receives structured evidence and returns data that conforms to a fixed schema. An agent cannot execute commands, edit the ledger, approve a result, or bypass the validator.

### 8.2 Deterministic components

The following components do not use an LLM:

- Environment probe
- Hugging Face revision resolver
- vLLM process manager
- Load generator
- Raw metric collector
- Metric reducer
- Candidate validator
- Trial scheduler
- Quick and full quality gates
- Frontier calculator
- Budget controller
- SQLite ledger
- Rollback manager
- Result renderer

## 9. Runtime design

Sera starts each vLLM configuration as a child process on a loopback port.

This design gives Sera:

- Process isolation between trials
- Access to the OpenAI-compatible request API
- Access to the Prometheus-compatible metrics endpoint
- Reliable teardown between configurations
- The ability to run two vLLM services on one GPU

A trial follows this sequence:

1. Resolve and pin the model revision.
2. Validate the candidate.
3. Start vLLM with an explicit configuration.
4. Wait for the health check.
5. Run warm-up requests.
6. Run the controlled load.
7. Collect request, engine, GPU, and process metrics.
8. Run the quick quality gate.
9. Run the full evaluator when required.
10. Write the result to SQLite and Weave.
11. Stop the exact child process.
12. Confirm that GPU memory returned to the pre-trial range.

Startup failure, timeout, out-of-memory failure, and teardown failure are trial outcomes. They must not crash the complete optimization run.

## 10. Measurements

### 10.1 Request measurements

Sera records:

- Request count
- Prompt tokens
- Generated tokens
- End-to-end latency at p50, p95, and p99
- Time to first token at p50, p95, and p99
- Time per output token at p50, p95, and p99
- Queue time at p50, p95, and p99
- Successful requests
- Failed requests

### 10.2 Engine measurements

Sera reads vLLM metrics for:

- Running requests
- Waiting requests
- KV-cache use
- Preemptions
- Prompt-token throughput
- Generation-token throughput
- Prefix-cache hits and queries

### 10.3 Hardware measurements

Sera reads NVIDIA telemetry for:

- Peak allocated GPU memory
- Peak total GPU memory use
- GPU compute utilization
- GPU memory-controller utilization
- Power use when available

Unavailable metrics are recorded as unavailable. Sera must not replace missing measurements with agent estimates.

### 10.4 Reduced evidence

The reducer converts raw measurements into a stable evidence record:

- p95 end-to-end latency
- p95 time to first token
- p95 time per output token
- p95 queue time
- Input tokens per second
- Output tokens per second
- Peak KV-cache use
- Peak GPU memory use
- Mean GPU compute use
- Mean memory-controller use
- Preemptions per request
- Error rate
- Difference from the baseline
- Remaining latency, quality, and memory margin

The reducer reports values. It does not state a cause.

## 11. Candidate space

Agents choose from a bounded, typed set of settings. They cannot invent vLLM flags.

### 11.1 Quantization

- Weight mode: baseline, supported FP8, supported 8-bit, supported 4-bit
- KV-cache data type: auto or supported FP8
- Model data type: auto, bfloat16, or float16 when legal

Sera exposes only methods supported by the installed vLLM version, model, and GPU. A missing compatible checkpoint or kernel makes a candidate illegal.

### 11.2 Batching and scheduling

- max_num_seqs
- max_num_batched_tokens
- max_model_len
- enable_prefix_caching
- chunked prefill when supported

Values come from a small policy-generated set based on prompt lengths, output limits, available KV cache, and observed queueing. Sera does not form their full Cartesian product.

### 11.3 Parallelism

- tensor_parallel_size

Tensor parallelism is active only when two or more GPUs are visible. Pipeline parallelism is outside the MVP.

### 11.4 Placement

- CUDA device assignment
- Per-service gpu_memory_utilization
- Per-service KV-cache budget

Placement is used only in phase two.

## 12. Proposal contract

Every specialist proposal contains:

- proposal_id
- agent_role
- parent_trial_id
- model_id
- one changed lever
- proposed value
- evidence used
- predicted metric change
- confidence from zero to one
- expected trial cost
- falsification condition

Initial proposals change one lever. After single-lever trials pass, the arbiter can request a combination trial. A combination must cite all parent trials and can contain only changes that passed alone.

The arbiter ranks proposals. It does not merge unrelated proposals into an untraceable candidate.

## 13. Search policy

Sera does not perform grid search during normal optimization.

Each round works as follows:

1. The reducer publishes the current evidence record.
2. Each active specialist returns zero to two proposals.
3. A specialist returns no proposal when its lever is inactive.
4. The arbiter ranks proposals by expected constraint relief, predicted gain, confidence, information value, and trial cost.
5. The deterministic scheduler removes duplicates and invalid candidates.
6. The scheduler selects up to three candidates without exceeding the reserved budget.
7. Trials run sequentially on Molab or concurrently on isolated GPUs.
8. Results enter the ledger.
9. The next round receives a digest of successful, failed, and reverted trials.

The scheduler selects one exploration trial from an untested legal proposal when the budget contains at least three remaining trials. This prevents the arbiter from testing only one familiar lever.

The loop stops when:

- The candidate budget is exhausted.
- Two complete rounds produce no frontier improvement.
- No legal untested proposal remains.
- The session has insufficient time for another trial and teardown.

## 14. Validation

The validator checks candidates before vLLM starts.

It checks:

- Model architecture support
- Quantization support for the installed vLLM and GPU
- Required checkpoint files
- Data-type support
- Positive and bounded batch settings
- Context length against model limits
- Tensor-parallel size against visible GPUs
- Tensor-parallel divisibility constraints
- Estimated weights, KV cache, runtime workspace, and safety reserve
- Sum of per-service GPU memory limits for joint placement
- Duplicate configuration hashes

The default joint-placement memory reserve is 10 percent of GPU memory. A candidate that only fits without the reserve is rejected.

## 15. Quality gates

### 15.1 Quick gate

Every executed candidate passes a cheap check before full evaluation.

The quick gate rejects:

- Startup or generation errors
- Empty outputs
- Non-finite logits or corrupt requests
- Severe output-length collapse
- Behavior-proxy score below the configured tolerance

Quick mode uses baseline outputs and a versioned external judge to produce a behavior-preservation proxy. This is not task-quality proof.

### 15.2 Full gate

Verified mode calls the user evaluator with the same evaluation examples for the baseline and every candidate.

A candidate passes only when:

- Its quality score meets the configured floor.
- Its latency requirement passes.
- Its error rate is zero unless the user explicitly allows errors.

Quality failure causes rejection and rollback even when performance improves.

## 16. Frontier

A configuration is viable when it passes feasibility, reliability, and quality gates.

A viable configuration is on the frontier when no other viable configuration is:

- At least as fast,
- At least as memory efficient, and
- At least as high throughput,

with a strict improvement in one of those measures.

The recommendation is selected from the frontier in this order:

1. Pass the quality gate.
2. Pass the latency requirement when supplied.
3. Minimize p95 end-to-end latency.
4. Minimize peak GPU memory as a tie-breaker.

Phase two re-scores the frontier for the smallest configurations that still satisfy the model requirements.

## 17. Joint placement

For two models, the frontier reader proposes:

- One viable configuration for each model
- GPU assignment
- Per-service GPU memory limit
- Expected contention risk

The fit check uses weights, KV cache, workspace, process overhead, fragmentation reserve, and the shared safety reserve.

If the candidate fits, Sera starts both vLLM services on the same GPU and runs both load generators at the same time. Each model receives the same workload it received alone.

The joint verdict is pass only when both models independently pass:

- Quality
- Latency
- Error rate

Sera compares shared and isolated results. It records the observed changes without assigning an unsupported cause. A failed joint trial is rolled back and its evidence returns to the reducer and specialists.

## 18. Ledger and Weave

SQLite is the source of truth for local execution and recovery.

The ledger stores:

- Run specification
- Environment fingerprint
- Model identifiers and revision SHAs
- Raw and reduced metrics
- Agent prompts and structured responses
- Proposals
- Validator decisions
- Trial configurations
- Trial states and timestamps
- Quality results
- Frontier membership
- Reverts
- Final recommendation

Each configuration has a canonical hash. Sera must not execute the same model, workload, and configuration twice in one run.

Weave mirrors the optimization as one root trace with child operations for:

- Baseline
- Reduction
- Each specialist
- Arbitration
- Validation
- Trial execution
- Quality evaluation
- Frontier selection
- Joint placement
- Revision after failure

Secrets must not enter SQLite, logs, reports, agent prompts, or Weave traces.

## 19. Benchmark against naive grid search

Naive grid search is an external benchmark control. It is not part of Sera's search implementation or public API.

The benchmark tests whether Sera's evidence-driven policy finds a stronger valid configuration within the same GPU-trial budget.

### 19.1 Candidate universe

A deterministic benchmark generator creates a small legal candidate universe before any method runs. The universe contains the same allowed values for Sera, fixed-order grid search, and random search.

The full universe is executed once to establish the oracle result. The evaluation harness then uses cached results to replay non-agent baselines without more GPU use.

### 19.2 Compared methods

- Sera with metrics, history, specialists, and arbiter
- Naive fixed-order grid search using a preregistered lexicographic order and no adaptive selection
- Uniform random search over 20 recorded seeds
- Sera without reduced telemetry
- Sera without trial history
- Round-robin specialists without the arbiter

All methods receive:

- The same candidate universe
- The same initial baseline
- The same trial budget
- The same measurements
- The same quality gate
- The same objective

The naive grid receives the same deterministic legality checks as Sera. This prevents invalid settings from creating a false advantage. The measured difference comes from trial selection.

### 19.3 Primary metric

The primary metric is trials required to reach a valid configuration whose p95 latency is within five percent of the oracle, with peak GPU memory as the tie-breaker.

Secondary metrics are:

- Best valid p95 latency at each trial count
- Peak memory at each trial count
- Invalid GPU trials attempted
- Repeated trials
- Quality failures
- Regret against the oracle

### 19.4 Passing result

The hackathon claim passes when Sera:

- Reaches the near-oracle threshold in fewer trials than naive fixed-order grid search, and
- Beats the median random-search result at the same budget, and
- Performs better than at least one intelligence ablation.

One lucky run is not evidence. Random-search results require recorded seeds and a distribution.

## 20. Intelligent ablation scenarios

The demonstration includes a dead-lever scenario.

On the one-GPU Molab environment:

- Tensor parallelism is impossible.
- Low queue time makes aggressive batching a low-value lever.
- High KV-cache use and preemptions make cache precision a live lever.

Sera must spend its first trials on the live lever. Fixed-order grid search and the round-robin ablation spend trials on settings that the evidence already marks as weak or impossible.

The benchmark includes a second scenario that reverses the pressure: high queue time and low KV-cache pressure must move batching ahead of precision.

These scenarios test whether Sera changes its search from evidence. They are not hand-coded answers for specific model IDs. The same reducer thresholds and proposal schema must apply to both scenarios.

## 21. Failure behavior

Sera must:

- Reject unsupported hardware before model download.
- Report missing API keys without printing secret values.
- Record model-download failure.
- Time out stalled vLLM startup.
- Record and recover from out-of-memory failure.
- Stop only the child process that belongs to the trial.
- Restore the last viable configuration after a failed candidate.
- Return baseline models when no safe improvement exists.
- Preserve the ledger after interruption.
- Resume without repeating completed trials.

The Molab notebook must:

1. Install Sera and its locked dependencies.
2. detect the RTX Pro 6000 GPU.
3. Resolve and pin both demonstration models.
4. Complete baselines.
5. Produce proposals from all active specialists.
6. Avoid a parallelism trial on one GPU.
7. Execute phase-one candidates.

9. Produce a frontier for each model.
10. Execute a joint trial.
11. Return two usable SeraModel wrappers or a clear no-safe-placement result.
12. Render the grid-search comparison and ablation.

## 23. MVP completion criteria

The MVP is complete when:

- The minimum two-argument API runs in Molab.
- A new user receives a usable runner and understandable summary.
- Every accepted recommendation is backed by measured latency, memory, and quality evidence.
- No agent can bypass deterministic validation or quality gates.
- The optimization loop visibly changes after a failed trial.
- Sera reaches the benchmark threshold in fewer trials than fixed-order grid search.
- The Weave trace shows the complete self-correcting loop.
- The same core library can run on a multi-GPU CoreWeave Linux host without notebook-specific code.
