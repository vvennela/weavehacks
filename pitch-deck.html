The problem02

Three choices decide how fast a model serves.

A GPU stalls for three different reasons. Each lever attacks one of them — and charges you for it.

Quantization
Store the weights in fewer bits.
Every number in the model is 16 bits. Make it 8. The model halves in size, and half as much has to cross the card for every token you generate.
BuysIt fits — and it moves faster.
CostsLess precision. Push too far and the answers degrade.
Attacks · memory + bandwidth
Caching
Don't recompute what you already computed.
Reading a prompt builds a working memory. When the next request opens with the same text — the same system prompt, the same document — reuse it instead of redoing it.
BuysSkips the expensive first pass. Answers start sooner.
CostsIt occupies GPU memory, and only pays when text repeats.
Attacks · repeated work
Batching
Run many requests through the card at once.
A GPU is enormously wide. One request at a time leaves most of it idle. Batching groups requests so a single pass over the weights serves many people.
BuysFar more total throughput from the same card.
CostsRequests wait for the group. The slowest one gets slower.
Attacks · idle compute
Also in the runGraph execution — pre-record the GPU's steps so it doesn't re-plan them for every single token.
The problem03

Turn one, and the others move.

01Quantize the weights and you free memory — so there's room for a much bigger cache. Which only pays off if your traffic actually repeats.
02Batch harder and throughput climbs — while the slowest request gets slower. Two goals, one dial, opposite directions.
03Cache aggressively and you spend the memory quantization just saved. The levers compete for the same card.
04Every combination is legal on paper. Most are not legal on your hardware — and you find out by waiting for a load that fails.
So people guess. Or they grid-search — and burn GPU hours on settings that were never going to fit.

AgentsThree investigators read the same measurements and propose experiments. They review each other and revise.

The run you're about to watch05

Seven phases. Three times over.

Qwen2.5-72B — about 135 GB of weights at 16-bit, on a 96 GB card. The baseline is already FP8; that is the only way it loads at all.

01
Inspect
All three investigators read the same evidence at once — load metrics, latency outliers, where requests wait. Nobody gets a private view.
02
Propose
Each proposes one configuration change and what it expects to happen. These are hypotheses — none of them is a result.
03
Peer review
They read each other and revise. In round one an agent withdrew its own memory change — zero preemptions, no evidence of a memory constraint.
04
Arbiter
One experiment is selected. When agents converge on the same change it costs one trial, not three.
05
GPU trial
The runner loads that configuration on the Blackwell, warms it, and drives fixed loads of 1, 2, 4 and 8 concurrent requests.
06
Measure
96 timed requests and 8 strict-JSON quality checks per configuration. The result goes back to the investigators.
07
Stop / return
A round with no qualifying gain buys one confirmation round. When that also misses the 5% bar, Sera stops, returns the best quality-valid configuration, verifies the runner answers a fresh request, and releases the GPU.

What peer review actually changed.

Phase 03 is the one people ask about. These are paraphrased from the recorded reasoning.

R1Agent B opened with “GPU memory allocation → 85%” and withdrew it after reading its peers: zero preemptions and no observed memory constraint. It backed A's caching test instead.
R2Agent A opened with “disable chunked prefill” and dropped it: small queue time gives little support for a scheduling bottleneck. All three converged on the graph test.
R3Agent B withdrew the allocation change a second time and accepted C's interaction test on the best parent — keep the measured cache win, change only graph execution.
→Convergence is not waste. Three agents agreeing costs one GPU trial, because the arbiter deduplicates identical proposals rather than running each one.
We are not claiming the swarm beats a single agent — one run per model, and the investigators often agreed. What is on record is that peer feedback changed the proposals, and that unmeasured hypotheses got withdrawn instead of tested.

What we are not claiming.

Say these before a judge finds them.

Not 19.77% faster than “normal”. It is 19.77% against Sera's own FP8 baseline. The 16-bit model never ran — it does not fit on the card, which is why the baseline is FP8.
Not proven faster than grid search. One exploratory three-candidate comparison. The specified benchmark is not finished.
Not your traffic. Eight easy tasks on warmed, repeated prompts. This establishes nothing about cold-cache performance or broad model quality.
Not a global optimum. The stopping rule ends the search when gains stop clearing 5%. That is a budget policy, not a proof.
Not a live endpoint. The recorded runner was verified, then closed, and the GPU released.
Not multi-GPU. One card. Two-model placement and broader hardware are later work.
