# SME technique map for the best measured kernel

## Peak reference and limits

The [University of Jena M4 SME microbenchmarks](https://scalable.uni-jena.de/opt/sme/micro.html) report 2,008 GFLOP/s for single-core FP32 FMOPA on a performance core (section “Peak Performance”). Their tile-reuse test rises from 503 GFLOP/s with one ZA tile to 1,005 with two and 2,008 with all four. This supports using four independent ZA accumulators; it is a synthetic microbenchmark, not a full GEMM result for this M4 Pro or this benchmark harness. A 2,000 GFLOP/s full call is 99.6% of that reported rate before packing, loads, output stores, and loop work. Treat 2,000 as an aggressive target, not a forecast.

Jena also reports that 64- and 128-byte LD1W microbenchmarks were slower than four-Z-register LD1W, which reached up to 925 GiB/s under its test, and that load alignment affected throughput. These are memory-copy microbenchmarks, not measured GEMM improvements. Arm’s [consecutive-register LD1W](https://developer.arm.com/documentation/ddi0602/2024-03/SVE-Instructions/LD1W--scalar-plus-immediate--consecutive-registers---Contiguous-load-of-words-to-multiple-consecutive-vectors--immediate-index--) and [strided-register LD1W](https://developer.arm.com/documentation/ddi0602/2024-03/SME-Instructions/LD1W--scalar-plus-immediate--strided-registers---Contiguous-load-of-words-to-multiple-strided-vectors--immediate-index--) documentation describes instruction forms; legal encodings and useful layouts still need to be checked against this kernel’s operands.

## What the exact best source already does

The inspected source is [`evidence/cpu-best-kernel-repeatability-2026-09-25/search/trial-001/source/kernel.c`](../evidence/cpu-best-kernel-repeatability-2026-09-25/search/trial-001/source/kernel.c), hash `eb091b1eca431f0760d0d61e4c0c6e748c1a9e34466a87ac15ad9cb238b5aecf`. At `gemm` (lines 769–780), n=512 calls `sera_libxsmm_panel32`; the nearby full-512 NN body is not the active 512 path. Other sizes use the unchanged fallback.

The active panel routine has one `SMSTART` at line 848 and one `SMSTOP` at line 1214 around the entire 16-band call. It allocates one 64 KiB scratch panel (lines 849–856), packs each 32-row A band into K-major form, and reuses that band across the 16 output-column panels (outer loops at 857 and 1041). Reducing transitions or merely moving to one SME region is already done.

In the active K loop, lines 1055–1066 set a 512-step count. Each step performs two paired LD1W instructions, one from B and one from the packed A panel, advances both pointers, then issues four FMOPA instructions to ZA0–ZA3. Each loaded A half is reused across two FMOPAs, and each B half is reused across two FMOPAs. All four ZA tiles are updated once per K step, so the documented four-tile dependency separation is present. Output leaves ZA through vector registers and is stored to C after the reduction; this follows Jena’s recommended ZA-to-Z store path (lines 1071 onward; Jena section “Bandwidth: ZA Array”).

## Distinct instruction-level work still applicable

- **K-loop lookahead or unrolling in the active panel routine:** the panel K loop currently branches once per K step and has no explicit next-step preload: `LD1W`, pointer advances, four FMOPA, decrement/branch (lines 1057–1066). Scheduling upcoming loads ahead of current FMOPA work, or unrolling several K steps while preserving each output’s FP32 update order, is different from the already-present four-ZA interleave. Prior four-step-unroll measurements changed the embedded NN kernel, not this active panel32 K loop. Any larger register schedule must be checked for spills, pointer bounds, and unchanged numerical tolerance.
- **Use wider multi-register loads with a compatible K micro-panel:** the current compute loop loads two registers per operand per K. Jena’s reported four-register LD1W bandwidth makes wider loads a supported hypothesis, not a speed claim. A contiguous multi-K load is not directly available from both current pointers: B advances by 2,048 bytes per K, while packed A advances by 128 bytes. A wider B load may require a new K-major B micro-panel or a documented strided-register form. Its packing, allocation, and memory traffic must remain in timed `gemm`; compare the complete call. Verify the applicable SME2 instruction form and compiler acceptance before editing.
- **Load/store alignment only as a measured complete-call change:** Jena reports alignment sensitivity for some load paths. The current scratch panel is stack-aligned by masking SP to 64 bytes (mask `0xffffffffffffffc0`; the allocation size is 64 KiB) (lines 841–850), while source matrix alignment is not controlled by this kernel. Changing scratch or input access alignment is distinct only if it changes the active panel body and source addressing; do not infer a benefit from Jena’s isolated bandwidth result.

More ZA independence is not available in the current four-tile design: the source already updates ZA0, ZA1, ZA2 and ZA3 on every K step. State-entry savings are also largely exhausted by one full-call streaming region. The remaining map therefore points to load scheduling, operand layout, and alignment interactions, with nontrivial implementation and timing costs. The exact source reached 1,701.65 GFLOP/s in one prior AC report, but its ten-run AC series did not pass the existing repeatability gate; a later Battery Low Power replay peaked at 1,108.66 GFLOP/s. These are different power-mode results and must stay separate. Neither establishes a 2,000 GFLOP/s result.
