# Approved live Sera versus grid comparison

This is an exploratory Qwen72B FP8 comparison approved by the user. It is not the original Qwen0.6B section 19 benchmark or a section 19.4 certification. The unchanged small-model task baseline failed its 99% gate. No task, expected answer, grader, or floor is changed here.

## Frozen contract

- Reference: pinned Qwen2.5-72B-Instruct, FP8 weights, BF16 KV, batch tokens 4096, context 4096, sequence limit 8, GPU fraction 0.9, eager execution, prefix caching off.
- Workload: the same eight easy strict-JSON tasks, original system prompt, 64-token generation limit, 99% quality floor, concurrency 1/2/4/8. Request p95 covers repeated prompts after per-load warmup.
- Three single-setting candidates: graph execution, batch tokens 2048, prefix caching. This is also their canonical grid order.
- Live Sera: the public Weave-backed three-investigator API with the exact frozen candidate hashes, no automatic space expansion, and `Budget(max_candidate_trials=None)`. Stop by plateau plus confirmation, exhausted legal space, or explicit agent/arbiter abstention. The finite universe has three configurations; that is not an added per-run trial cap.
- Each candidate selected by Sera is measured immediately. Later investigators receive only prior results. After Sera stops, the returned runner receives one fresh request on the unchanged first task and is closed. Only then can missing frozen configurations be measured for the oracle.
- The full grid is replayed on these identical outcomes. It does not receive an independently noisy GPU run. The saved live Sera sequence is replayed for scoring; agents are not invoked again for this step.

Prior 72B demo results informed the small control selection. This is disclosed in the frozen registration. No prior timing becomes a fresh measurement or is given to the live agent as a benchmark outcome. The prior run supplies only pinned hardware/runtime/model identity and exact rendered input tokens, checked again during the new run.

## Commands

Run from the source checkout. Configure the same `SERA_AGENT_PROVIDER`, `SERA_AGENT_MODEL`, `SERA_PROJECT`, `SERA_PROVIDER_CHECK`, `SERA_RELAY_DIR` (for Codex relay), and `WANDB_API_KEY` used by the public swarm API. Keep its matching local controller running. No new provider certificate is generated by these commands.

First freeze, without GPU or provider calls:

```bash
python -m benchmarks.live_comparison freeze \
  --reference evidence/live-luna-expanded-v2/result.json \
  --output-file /marimo/sera-evidence/grid-comparison-registration-v1.json
```

Start the real live loop in a fresh process:

```bash
python -m benchmarks.live_comparison run-live \
  --registration /marimo/sera-evidence/grid-comparison-registration-v1.json \
  --output-dir /marimo/sera-evidence/live-grid-comparison-v1
```

The output directory must be new. The driver saves registration and launch records before calling Sera. A benchmark-scoped runtime subclass measures the complete owned server interval, including time waiting for investigators; normal serving, selection, and cleanup code are unchanged. Startup-ready time is separate. A failed start records its observed start-call interval. No failed trial receives an invented latency or task score.

After the process completes successfully and the runner is closed:

```bash
python -m benchmarks.live_comparison import-live --run-dir /marimo/sera-evidence/live-grid-comparison-v1
python -m benchmarks.live_comparison collect-missing --run-dir /marimo/sera-evidence/live-grid-comparison-v1
python -m benchmarks.live_comparison compare-grid --run-dir /marimo/sera-evidence/live-grid-comparison-v1
```

Only `run-live` and `collect-missing` make GPU calls. Only `run-live` calls investigators. Import and scoring are offline.

Import checks the registration/result hash binding, exact model/configuration/workload, live stopping settings, chosen order, saved history/inspection scopes, passed fresh runner probe, cleanup, and actual owned-runtime timing. It regrades saved answers and recomputes request p95 through the collection adapter. Original pipeline trial IDs remain in source records; comparison candidate IDs are full configuration hashes. The measured reference costs zero search trials. Using the explicit FP8 reference avoids counting an earlier fit-first deployment as a search trial.

Missing collection never remeasures an imported candidate. Existing incomplete candidate folders require an explicit source audit, not a blind retry. Startup/task failures remain in the universe. Cleanup failure stops collection. Missing or mismatched outcomes block oracle and grid scoring.

## Preregistered result rule

The oracle is the lowest p95 among all completed configurations passing the frozen feasibility, reliability, and task gates; sampled peak GPU memory breaks latency ties. A search reaches the near-oracle target when its best valid measured p95 is at most 1.05 times oracle p95.

Count the reference as trial zero. An exploratory Sera search win requires Sera to reach this target before grid. Unreached remains null, not a fabricated trial count. A tie, including a reference already near the oracle, is not a win. Report terminal latency and the complete search trajectories separately.

This evidence score is not deployment approval: the live returned runner still follows Sera's unchanged 5% improvement target. The two 5% rules mean different things. Startup and total GPU collection time are reported separately from request latency. Summed provider attempt durations include parallel calls and are not end-to-end wall time.

No random-search or ablation runs are part of this pass. `strict_section_19_4_claim` is always false. Tests use labeled fixtures; fixture wins do not permit model-performance claims. A real single-profile win establishes this observed comparison, not global optimality, statistical significance, or general agent superiority.
