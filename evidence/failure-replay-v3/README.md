## Outcome

- All three investigators successfully read evidence in both rounds.
- Round one selected a legal batch-token proposal.
- Round two correctly kept the baseline with zero trial budget.
- All recorded mechanical criteria passed; factual reasoning did not.

Five additional inspection choices were invalid and rejected. Each investigator
still completed a real read; passing the loop checks does not mean every tool
choice was valid.

The explanations no longer repeat the earlier 2,265-tokens-per-request claim,
and they now name the startup CUTLASS error. That is an improvement in the
observed responses, not proof that diagnosis is reliable.

Concrete remaining errors:

- Scheduling and memory/context rule out scheduling or memory as a startup
  cause, although the supplied diagnosis says the root cause is not established.
- All three first-round refined explanations give a 735.3 ms latency target;
  the exact 5% target is 735.4738642498432 ms.
- The final output-quality explanation says memory did not change. Both values
  were supplied: 88,687 MiB baseline and 88,561 MiB candidate, a 126 MiB reduction.
- Memory/context says a future *worse* configuration would refute keeping the
  baseline. That reverses the direction of the decision test.
- Explanations still propose pressure-relief benefits without evidence that
  this workload is pressure-limited. A hypothesis is not a measured mechanism.

The historical candidate passed 8/8 tasks but improved worst-load p95 by only
0.054228%, below 5%. Keeping the baseline is correct; a correct final action does
not make every supporting claim correct.

## Evidence limits

The run used derived failure diagnoses, bounded trace records, and only one
legal first-round candidate. It does not prove independent startup root-cause
discovery, search superiority, proposal diversity, or performance on unseen
failures. The raw report deliberately retains `factual_reasoning_verified=false`.

All five downloaded raw artifacts matched their remote byte hashes. The local
arithmetic check reproduced prompt lengths, average tokens, the latency target,
the 0.054228% gain, and matching task answers. No failing record was overwritten.

The [offline audit](verification.json) matched all 27 provider attempts, all 25
compact prompts, and all 282 copied source records. Both helper revisions produce
identical prompts for this scenario. The missing-quality-label fix therefore
does not change the inputs used for the next model comparison.
