# Untested AOT-kernel directions for the next Sera swarm

The measure-prepared run rejected or declined promotion of the software-pipeline, pointer-end, and two-step K-unroll variants; noisy controls also limit causal claims. Its README says the next selected cache-blocking/vector-access ideas were not implemented because one already existed in the reference and the other required an unsupported paired-load form. `agent/state.json` records 71 model calls and 6 implementation attempts. No packing, output-store, or tile-order change was measured in that completed run.

The n=512 path in [`editable/kernel.c`](../cpu-libxsmm-reference-2026-09-24/editable/kernel.c) calls the fixed AOT LIBXSMM kernel. Do not mistake the general-size fallback for the timed path: only `n != 512` calls `fallback_gemm`, which allocates a full `n*n` A-transpose buffer. The AOT path enters SME once, reserves 128 KiB of aligned stack scratch per outer block, transposes/repacks one operand into that scratch with a ZA row/column transfer loop (`Llibxsmm_78`), then feeds it through paired `LD1W` loads and four `FMOPA`s per K step (`Llibxsmm_70c`). The other operand is loaded directly from the caller's matrix. Its four ZA tiles are zeroed for beta=0; C is not read.

1. **Pack a bounded B panel alongside the existing A scratch panel.** Test packing a small K-by-32-column B panel so both operands arrive contiguous to the K loop, reusing the B panel across adjacent M tiles where the traversal permits. Include packing in the timed call and compare panel sizes that leave L1 capacity for C and other live data. Current M4 P-core L1D is 128 KiB; the AOT path already reserves 128 KiB of scratch, so simply adding another full-sized panel is not a sound design. This differs from the existing one-operand ZA transpose and from rejected K-loop changes.

2. **Change how the four ZA tiles reach C.** The current path extracts ZA horizontal slices into Z-register groups with `MOV`, then issues paired `ST1W` stores for adjacent vectors and advances row addresses by 0x800 bytes. It already has beta=0 write-only output and does not use the earlier proposed ZA-to-SVE-indirect store idea as a new feature—that transfer is present. A distinct test is SME ZA slice-to-memory stores, or a rearranged store grouping that removes some ZA-to-Z transfer/address instructions while preserving the same 32x32 tile and each C element's single write. Total output bytes cannot fall below one write per element; the hypothesis is lower store instruction cost. Verify the exact SME2 form and all output rows before timing.

3. **Revisit the output macro-tile traversal to reuse packed data and nearby C lines.** The existing assembly has a 512-count outer loop stepped by 64 (`Llibxsmm_64`) and a 512-count nested tile loop stepped by 32 (`Llibxsmm_440`); it prepares scratch for the outer block and computes fixed 32x32 ZA tiles. Test one alternate M/N tile order or a two-adjacent-tile macro-step that keeps a packed panel live and writes neighboring 128-byte C row segments close together. Do not change the K schedule or infer cache-set conflicts. This is an unmeasured cache/reuse hypothesis; keep allocation and packing costs inside the hill call.

All candidates must preserve the AOT 512 dispatch and general-size fallback, beta=0 semantics, 0.002 numerical tolerance, and existing single-thread frozen hill. No performance gain is established by this note.
