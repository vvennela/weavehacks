# Duplicate board nominations audit

## Finding

Round 1 selected `streaming_region_cost`, `cache_blocking`, and `n512_fast_path` as its three experiments. They are three role IDs for one source change: loop over the existing panel32 pack/compute body for the sixteen 32-row bands inside one SME region, with one scratch allocation and pointer resets. The first recommendation describes the assembly helper loop; `cache_blocking` describes the same one-entry panel32 traversal; `n512_fast_path` describes moving that same 16-band loop into a single-entry wrapper. Their source operations and expected output mapping overlap; Astra confirmed both later proposals were semantic duplicates of measured source hash `eb091b1e…` and abstained.

The ballots show this was not three distinct high-value options. Of 15 complete ballots, 14 ranked `streaming_region_cost` first; one ranked `n512_fast_path` first. Nevertheless all three aliases occupy the top-three Borda slots, and the selected `experiment_order` contains all three. `rank_experiments` scores every distinct string ID as an independent proposal, so each alias gets its own score and batch slot. Because duplicate detection happens during Astra implementation, the two later proposals consume two implementation calls and two of the six `proposal_count` slots, then force the next board round. The shared board still costs its normal coordinator, advisor, and ballot calls.

Evidence: [`state.json`](agent/state.json), round 1 `board`, `ballots`, `experiment_order`, and `implementations`; [`kernel_advisory.py`](../../sera/kernel_advisory.py#L238-L266); [`kernel_swarm_plan.py`](../../sera/kernel_swarm_plan.py#L4-L17). The implementation-time duplicate check is in `kernel_advisory.py` around `_implement` lines 300–340.

## Smallest compatible correction

Add a required `change_signature` string to the existing advice response. Define it as a compact, normalized identity for the actual proposed source change: source anchor(s), operation/control-flow change, and affected data layout. Keep the advisor role ID as provenance. Before constructing the voting board, group only exact matching signatures into one experiment entry and retain every source recommendation and role in that group. If signatures differ or grouping is ambiguous, leave the entries separate; do not merge by topic words such as “cache” or “fast path.”

Vote over grouped experiment IDs rather than role IDs, then run Borda on each full permutation of distinct groups. Newly collected ballots contain no separate aliases to collapse. Collapsing aliases in historical ballots can illustrate the change, but cannot substitute for a fresh grouped-board vote. This prevents multiple synonyms from earning multiple ballot positions or occupying several batch slots. The proposal payload can show the combined descriptions and risks, while the tie-break ID is a stable signature-derived ID. Abstentions remain unchanged.

This fits the current API with no extra model call: add one required field to `ADVICE_SCHEMA` and its response validation, then group board entries before creating the existing ballot schema. It leaves the 15 advice and 15 vote calls per complete board unchanged. If the advisors assigned the same signature to the three observed duplicates, grouping would select one representative and could save two Astra implementation calls and two of the six implementation slots; the top-three limit would then admit two distinct proposals. It adds response tokens and grouping code, but no new quality, timing, or promotion policy.

Risk: advisors may assign different signatures to paraphrases, so exact grouping can miss semantic duplicates; an overly broad signature can merge distinct changes. Add pure tests for identical signatures collapsing, distinct signatures remaining separate, provenance retention, collapsed ballots being full permutations, and Borda order on distinct groups. If stronger semantic grouping is preferred, a separate Astra deduplication call before voting is clearer but costs one extra model call per board (up to six under the current six-round cap) and consumes the existing 108-call budget; it can displace later implementation/review calls when the budget is tight.
